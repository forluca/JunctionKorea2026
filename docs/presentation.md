# Docket — 발표 정리 (JunctionX Korea 2026, Upstage 트랙)

> **펀치라인**: "여행 문서를 던지면, 여행이 됩니다."
> 예약 메일·PDF·티켓을 지도 위에 끌어다 놓는 순간, AI 에이전트가 읽고 분류하고 추출해서
> 일정·지도·캘린더까지 알아서 정리하는 여행 문서 에이전트.

심사 기준: **Upstage 기술 활용 30% · 창의성 25% · 기획 25% · 완성도 20%**
아래 각 섹션이 어느 기준을 공략하는지 표시해 두었습니다.

---

## 1. 문제 정의 (기획 25%)

- 여행 준비는 **문서와의 싸움**이다. 항공 e-Ticket, 호텔 바우처, 입장권, 여행 계획서가
  메일함·카톡·다운로드 폴더에 흩어져 있다.
- 여행자는 같은 정보를 **세 번** 옮겨 적는다: 일정표에 한 번, 캘린더에 한 번, 머릿속에 한 번.
- 현장에서는 QR 티켓을 찾느라 메일함을 뒤지고, 일정이 겹치는 실수는 공항에서야 발견된다.
- 기존 여행 앱은 **직접 입력**을 요구한다. 우리는 입력 자체를 없애고 싶었다.

**핵심 질문**: "문서를 그냥 던져 놓으면, 나머지를 전부 AI가 해줄 수는 없을까?"

## 2. 솔루션: Docket (기획 25%)

- **입력은 드래그 앤 드롭 하나**. 지도 화면 어디에든 PDF/이미지를 끌어오면 끝.
- 문서 종류를 사용자가 고르지 않는다 — **에이전트가 스스로 분류**한다
  (호텔 바우처 / 교통 e-Ticket / 투어 입장권 / 여행 계획서).
- 결과물은 자동으로:
  - **타임라인**: 날짜별로 구분된 일정 (체크인/체크아웃 분리, 시간순 정렬)
  - **지도**: 일정별 핀 + 원본 문서 썸네일 말풍선
  - **캘린더**: Google Calendar 이벤트 + 무료 취소 기한 리마인더
  - **보관함**: 여행별로 그룹핑된 원본 문서 아카이브 (QR 코드 크롭 포함)
- 에이전트가 단순 저장을 넘어 **판단**한다: 중복 문서는 거절하고, 시간이 겹치는 일정은
  충돌로 표시하며, 여행 기간은 새 문서가 들어올 때마다 스스로 넓어진다.

## 3. 라이브 데모 시나리오 (완성도 20%)

> 문서 1건 처리에 30~45초 소요. 처리 대기 시간에 아키텍처 설명을 끼워 넣을 것.

1. **로그인 → 메인 화면**: 풀스크린 지도 + 좌측 플로팅 패널. "앱이 아니라 지도가 주인공입니다."
2. **여행 계획서 드롭** (`paris_4n5d_itinerary.pdf`):
   - 파일을 창 위로 끌어오는 순간 지도 영역 전체가 파란 점선 드롭존으로 확장 —
     "여기에 놓으면 여행이 시작됩니다".
   - 하단 알약에 에이전트 단계가 실시간 표시: 문서를 읽는 중 (1/5) → 유형 분류 (2/5) →
     핵심 정보 추출 (3/5) → 일정 정리 (4/5) → 캘린더 등록 (5/5).
     **→ 이 대기 시간에 4번(아키텍처) 설명.**
   - 새 여행 카드가 생기고 4박 5일 일정이 통째로 타임라인에 들어온다.
3. **바우처 추가 드롭** (콜로세움 입장권): 열린 여행 위에 드롭 → "여기에 놓으면 여행에
   추가됩니다" → 일정 추가 + 지도에 파란 풍선 핀 + Google Calendar 이벤트 등록 확인.
4. **일정 클릭**: 지도가 해당 핀으로 이동(패널을 제외한 영역 중앙 정렬), 문서 썸네일
   말풍선, 상세 패널에 예약번호·금액·취소기한·**QR 코드 원본 크롭** 표시.
5. **중복 문서 다시 드롭**: 즉시 거절 — "문서가 중복되었습니다" (409).
   "에이전트가 저장 전에 스스로 검증합니다."
6. **시간 겹치는 문서 드롭**: 저장은 되지만 **빨간 핀 + 충돌 배지**로 경고.
   "막는 게 아니라, 사람이 판단할 수 있게 알려줍니다."
7. **문서 보관함**: 여행별 그룹핑된 원본 아카이브. 클릭하면 원본 PDF.
8. (여유 시) 다크 모드, 여행 검색, Google 로그인 게스트 모드.

## 4. 아키텍처 — Upstage 기술 활용 (30%)

### 4-1. Upstage Studio Agent가 파이프라인의 심장

- **Upstage Studio에서 설계한 Agent 파이프라인**을 v2 API(`/v2/files`, `/v2/responses`)로 호출:
  **Parse(Document Digitization) → Classify → 유형별 Extract → 최종 Orchestrate**.
- `include=["all"]`로 **중간 단계 산출물을 전부 수확**해서, 최종 답변뿐 아니라 각 단계의
  파싱/분류/추출 결과를 코드에서 독립적으로 활용한다.
- 파이프라인 개선은 **Studio 웹 UI의 시스템 프롬프트**로 반복 실험 — 코드 배포 없이
  에이전트 품질을 튜닝했다. (예: 문서에 실제 등장하는 이름만 쓰도록 환각 방지 규칙,
  JSON 출력 강제, 근거 문장 인용 규칙)

### 4-2. LangGraph로 감싼 에이전트 오케스트레이션

```
ingest → [ Studio Agent ∥ QR·바코드 디코딩 ] → act
```

- **ingest**: 파일 저장(Supabase Storage) + 전처리.
- **Studio Agent 노드**와 **QR 디코딩 노드**(zxing-cpp + PyMuPDF)를 **병렬 실행**.
- **act**: 에이전트가 결정한 액션(add_to_itinerary / register_calendar / record_expense)을
  툴 레지스트리로 실행. targetType(schedule/trip)은 여행 생성 여부만 결정하고,
  바우처/여행계획서 분기는 **에이전트가 내부에서 스스로** 한다.

### 4-3. LLM 출력을 프로덕션급으로 만드는 방어층 (창의성과 겹침)

LLM 파이프라인의 현실적 불안정성을 코드로 흡수했다:

- **코드 펜스/인용 마커/이중 인코딩 제거** 후 JSON 파싱, 키 드리프트 별칭 체인
  (`normalized_item`/`itinerary_item`/`item` 모두 수용).
- 최종 단계가 빈 객체나 마크다운 산문을 내면 **Extract 단계 산출물로 폴백**해서
  일정을 재구성 (`Day N` → 기준일 + N-1 계산 포함).
- 액션 규칙을 코드에서 강제: 일정은 항상 저장, 시작 시각이 있으면 캘린더 등록,
  금액이 있으면 비용 기록 — 에이전트가 빠뜨려도 코드가 보완.
- 결과: **실제 여행 문서 7종 데이터셋 전부** 파이프라인 통과 검증.

### 4-4. 사용한 Upstage 기술 요약

| 기술 | 용도 |
|---|---|
| Studio Agent (v2 API) | Parse→Classify→Extract→Orchestrate 전체 파이프라인 |
| Document Digitization | PDF/이미지 → 구조화 HTML, 도형(figure) 좌표 |
| Document Classification | 문서 유형 자동 분류 (카테고리 설명 프롬프팅) |
| Information Extraction | 유형별 스키마 기반 필드 추출 |
| Solar | 백오피스 실험 및 JSON 스키마 응답 검증 |

## 5. 차별점 / 창의성 (25%)

1. **"업로드 폼"이 없는 UX** — 화면 전체가 드롭존. 파일이 창에 들어오는 순간 지도가
   드롭존으로 변하고, 하단 알약이 에이전트의 사고 단계를 중계한다.
2. **에이전트가 판단한 결과가 UI 언어가 됨** — 중복은 거절(409), 충돌은 빨간 핀,
   판단 근거는 일정의 '참고 사항'으로 남는다. AI의 판단이 블랙박스가 아니다.
3. **QR/바코드를 데이터가 아니라 자산으로** — 디코딩 값과 함께 **원본 이미지 크롭**을
   저장해서, 현장에서 바로 스캔 가능한 티켓 지갑이 된다 (QR/DataMatrix/Aztec/PDF417/1D 지원).
4. **여행 기간의 단조 확장** — 문서가 들어올수록 여행 범위가 스스로 넓어지고
   절대 줄어들지 않는다. 교통편은 출발일만 반영하는 등 도메인 규칙 내장.
5. **문서 썸네일 말풍선 핀** — 지도에서 일정이 아니라 '문서'가 보인다.
   원본과 일정의 연결이 항상 유지된다.

## 6. 완성도 (20%)

- **E2E 완주**: 드롭 → Studio Agent → DB 저장 → 타임라인/지도/캘린더/보관함까지
  실데이터로 전 구간 동작. 목업 없음.
- 실제 여행 문서 7종(호텔/교통/투어 4종/여행계획서)으로 품질 검증 완료.
- Google Calendar OAuth 실연동 (이벤트 + 취소 기한 리마인더).
- 충돌/중복 정책, 시간대 정규화, 한글 파일명 스토리지 이슈 등 엣지 케이스 처리.
- 대기 시간 UX: 카드 차오르기, 단계 멘트 알약, 스켈레톤 로딩, 날짜 구분선 등 디테일.
- 백오피스(8001): Upstage 단계별 실험 + DB 브라우저 — 개발 중 품질 검증 도구까지 제작.

## 7. 로드맵 (기획 25%)

- **영수증 확장**: record_expense 액션을 실비 정산으로 — 여행 가계부 자동화.
- **웹훅/알림**: 처리 완료·충돌 발생 시 푸시. 장기적으로 메일함 연동(전달만 하면 등록).
- **다인 여행**: 여행 공유, 동행자별 문서 병합.
- **모바일**: 현재 반응형 웹 → 카메라 촬영 즉시 등록.
- **다국어 문서**: Upstage 파이프라인은 이미 다국어 파싱 가능 — 스키마 확장만 필요.

## 8. 예상 질문 & 답변

- **Q. Classify/Extract를 직접 호출하면 되는데 왜 Studio Agent인가?**
  A. 파이프라인 설계·프롬프트 튜닝을 Studio에서 하고 코드는 호출과 방어에 집중하는 분업이
  개발 속도를 크게 높였다. 중간 단계 수확(include=all)으로 유연성도 유지했다.
- **Q. LLM이 틀리면?**
  A. 3중 방어: (1) Studio 시스템 프롬프트의 환각 방지 규칙, (2) Extract 산출물 폴백,
  (3) 코드 강제 액션 규칙 + 중복/충돌 검증. 문서에 없는 정보는 만들지 않는 것이 원칙.
- **Q. 가격이 이상한 문서는?**
  A. 문서에 적힌 값을 그대로 신뢰한다(문서 충실성 원칙). 재발행 티켓의 1,400원도
  문서에 실제로 적힌 금액이었다. 판단이 필요한 경우 '참고 사항'으로 사용자에게 알린다.
- **Q. 에이전틱하다고 할 수 있나?**
  A. 목표(여행 정리)만 주면 분류→추출→판단→툴 실행(일정/캘린더/비용)을 스스로 결정한다.
  중복 거절과 충돌 판정은 에이전트+코드의 협업 판단이다.
- **Q. 보안/키 관리는?**
  A. 모든 키는 .env(gitignore), 문서 원본은 Supabase Storage 서명 URL(24h)로만 노출.
